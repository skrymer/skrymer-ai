# Core orders the sign-off's gates, a project selects them, and every judgement runs in a fresh read-only agent

`core:feature-sign-off` runs the checks a functionally complete change passes before it is pushed. Each project needs a different set: a backend with no screen has nothing to walk through, and a project may not want a mutation sweep yet. But the gates' order is not a preference. Simplification comes before the mutation sweep so the sweep mutates the code that ships, the sweep comes before review so its new tests get reviewed, and verify runs last so nothing changes under it. A project that reordered them would break the reason each sits where it does.

So the project config's `signOff.gates` is a set, not a sequence. Core owns the order (simplify, mutation, code-review, check-adrs, verify), and the sign-off runs the selected gates in that order whatever order the config lists them in. An unknown gate name is a load error listing the valid ones. `mutation` and `verify` are engine gates: each runs once per stack root whose pack provides the engine, and selecting one when no enabled pack provides it is a load error. With no `signOff`, every gate whose engine is available runs. Four parts of the run are not gates and cannot be deselected, because they keep the run honest rather than check the code: the adversary, the acceptance ledger, the resolutions pass and the retro. Before any agent is spawned, each touched stack runs its pack's `check` command (the full build and tests, which a stack can override), so a branch that doesn't build stops before it costs anything.

Every judgement in the run comes from a fresh agent that holds only its brief, never from a fork of the author's conversation and never from the author. A fork carries the author's reasoning and starts from the author's conclusion. The recurring judging roles (code-reviewer, adversary, acceptance ledger, check-adrs, resolutions, blind arbiter, verdict auditor, retro miner) are core agent definitions in `plugins/core/agents/`. Each holds its fixed contract, and a brief carries only the per-run slots, so a brief can't drop an angle or soften a rule without the pack showing it. Each lists its tools, none of which writes (no Edit, Write or `memory`), and runs with `model: inherit`. The protection is the fresh context, not a different model, so a judge runs on whatever model the session uses. A test over `plugins/*/agents/` holds all of this.

A plugin agent can't be confined to read-only shell commands: plugin agents ignore `permissionMode`, and removing Bash would leave the judges unable to run `git diff` or read the issue. So each judge keeps Bash, and its definition forbids writing. That is a written rule, not an enforced one, and the resolutions pass can see a breach in the transcripts.

## Considered options

- **The project lists the gates in the order to run them.** That is simpler to explain, but every project would carry the order, and one that reordered the gates would run a review on code that is about to change.
- **Fork the conversation for each judge.** A fork is cheap and already knows the change, but it also knows why the author thinks it is right, and that is what a judge must not start from.
- **A different model for the judges.** It might add some independence, but the bias a judge must not have comes from what it is told, not from which model it runs on, and pinning a model costs every project a choice it doesn't need. The break-it tester (#53) is the one exception, run on Opus for the breadth of its exploration rather than its neutrality.
- **Keep the briefs as full templates in the skill.** That is how the sign-off started. A template copied into a prompt drifts from its source with nothing to show it. A contract in an agent definition is the same text every run.
- **Drop Bash from the judges to make read-only enforceable.** The judges then can't measure the diff or read the issue, which is most of what they do.
